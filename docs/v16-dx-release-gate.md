# V16 developer-experience gate

## Future architecture

FUTURE RUNTIME ARCHITECTURE: PASS WITH CONDITIONS

The runtime owns fixed parsed structure and a compiled visual timeline. Parameter state is a separate dictionary; `Bind` captures stable values, never a history of updates. Snapshots already support scene evaluation and MIDI as well as WAV, so state semantics are independent of a whole-file audio encoding. A future session can capture a snapshot at a render boundary and retain its own clock, buffers, smoothing, providers and output adapters. Incremental DSP remains separate future work; V16 does not promise that the current whole-file renderer can become incremental without new rendering work. No streaming API or device dependency is added here.

Review found one lifecycle usability gap: a host could not reuse an already compiled structure for independent state without compiling again. The contained `CreateInstance()` addition creates default state over the same private structure. It does not reinterpret `CompileRuntime`, copy another instance's current values or expose the AST. Managed instances and snapshots hold no device or file handles; ending a session means releasing references, not calling a fabricated disposal API.

## Final findings

1. **Future runtime compatibility:** PASS WITH CONDITIONS. The seam supports a future session consuming stable snapshots at render boundaries without changing V16 parameter meanings. The future incremental renderer must still implement clocks, buffering, active audio state and smoothing; V16 does not claim live synthesis.
2. **Workflow:** compile, discover defaults/ranges, render, set before/after first render, batch update, no-op update, reset, retain an old snapshot, release references, and create independent default state from the same structure were exercised.
3. **Lifecycle:** added `CreateInstance()` to reuse compilation without sharing state. Instances/snapshots own managed data and need no `Dispose`; retained snapshots remain valid after hosts release the runtime. There is no artificial disposed state to test. Playground operations before successful compilation report a useful error.
4. **Invalid/boundary inputs:** unknown/case-mismatched/blank/null names; null/string/integer/double/NaN/infinity values; exact limits and values outside them; duplicate/unused declarations, missing defaults, name collisions and unsupported structural/expression targets. All defaults are required in source, so no unresolved required parameter exists at runtime.
5. **Concurrency/snapshots:** tests interleave 5,000 yielding atomic state updates with four render readers; each snapshot matches one complete allowed state across WAV and scene. A separate concurrent test verifies retained WAV/MIDI snapshot output during updates. Old snapshots remain unchanged. One invalid batch preserves values, revision and cached snapshot; later valid updates recover. Bind once for matching media; separate convenience calls may observe separate revisions.
6. **Instance isolation:** separate instances start at declared defaults/revision zero over the same private structure; updates and resets do not leak across instances. No source parsing occurs during instance creation.
7. **Compile-once guard:** permanent 10,000-update production regression asserts tokenization, parsing and timeline compilation counts remain 1/1/1, and retained outputs stay stable. The sample benchmark reaches 140,042 revisions with the same counts. Timings are supporting evidence, not the guard.
8. **Ownership:** source is an immutable string parsed into private structure; metadata is read-only; caller mutations of returned WAV/MIDI/scene projections do not change later renders. The legacy MIDI interpreter receives private notation copies. Cached Wordbank audio copies both incoming registration data and returned bytes. External assets and process-global corpus configuration must remain stable while rendering.
9. **Cross-surface equivalence:** the canonical console/web/Playground sources match for normal/warning/critical WAV/MIDI/scene in a permanent test. Actual browser and package-backed HTTP WAV hashes match console/API for normal and critical. Actual CLI canonical MIDI matches all three states; CLI ordinary Wave matches a static literal reference in regression tests. `RenderAudio` includes visual padding while CLI Wave intentionally retains ordinary unpadded semantics.
10. **Diagnostics:** errors identify name/category/received value/range where applicable, show case-sensitive available names, and explain decimal literals. Empty schemas get an explicit message. Source parser errors retain existing position context. Rejected values preserve usable last output; no stack traces or resource payloads are needed for routine correction.
11. **API/CLI adjustments:** contained `CreateInstance()` addition; concise revision/value `ToString()`; clearer wrong-type/unknown/range errors; CLI empty-schema feedback. No overlapping alternate workflow or speculative session API was introduced.
12. **Capabilities inventoried:** Music/Wave, Studio, Audio/Visual, transcription, runtime, examples, editing aids, navigation, validation, playback and exports listed above were retained. Existing tests/goldens were not weakened.
13. **Playground layout:** wider bounded workspace; adjacent runtime source and output on desktop; stacked layout on narrow screens; visible primary compile/load actions; explicit validation feedback; mobile visual-stage overflow corrected.
14. **Editor:** main editor receives more usable responsive height; runtime textarea is resizable, labeled and spellcheck-free, with source length/help and visible focus. No heavyweight editor dependency was added.
15. **Grouping/position:** source actions stay with authoring; discovered values/apply/reset stay together; audio/download and scene appear beside them. Existing navigation keeps music, Studio, media and transcription discoverable.
16. **Data-driven controls:** parameter labels, defaults, bounds and values come from production metadata. Static programs show an explanatory empty state. The web sample now validates using returned metadata and accepts valid decimal positions instead of imposing a duplicate integer-only rule.
